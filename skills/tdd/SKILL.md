# Test-driven development

The failure this prevents: a test written after the code, which passes on its first run and
therefore proves nothing. You never saw it catch anything, so you do not know whether it
tests the behaviour or merely describes the implementation you happened to write.

**If you did not watch it fail, you do not know what it tests.**

## 1. Agree the seam first

A **seam** is the public boundary you test at: the interface where behaviour is observable
without reaching inside. Tests live at seams.

Before writing a test, name the seam and confirm it. You cannot test everything, and
agreeing the seam is how the effort lands on the critical path instead of on every edge
case. If naming it is hard, the interface is unclear — that is a design finding, report it
before writing tests around the confusion.

## 2. One slice at a time

One seam, one test, one minimal implementation, then repeat. Each test is a tracer bullet:
it responds to what the last cycle taught you.

Writing all the tests first and then all the implementation looks efficient and is not.
Bulk tests verify imagined behaviour — you commit to a test structure before understanding
the implementation, and the tests come out insensitive to the changes that matter.

## 3. Red, and red for the right reason

Run the test and read the failure. It must fail because the behaviour is missing, not
because of a typo, an import error, or a fixture that never loaded.

A test that passes on its first run is testing something that already worked. Find out
what, and fix the test.

## 4. Green, minimally

Write the least code that passes. Not the parameterised, configurable version you can
already picture — that version is unverified surface, and the test does not cover it.

Then run the whole relevant suite: one green test beside two newly red ones is not progress.

## 5. Refactoring is not part of this loop

Clean-up belongs to review, on a green suite, as its own change. Folding it into the cycle
means a failure has two candidate causes.

## Tests worth keeping

Verify behaviour through the interface. Implementation can change entirely; the test should
not.

Three shapes to recognise and reject:

- **Implementation-coupled** — mocks internal collaborators, reaches for private methods,
  or checks a side channel (querying the database instead of asking the interface). The
  tell: it breaks when you refactor while behaviour is unchanged.
- **Tautological** — the assertion recomputes the expected value the way the code does
  (`expect(add(a, b)).toBe(a + b)`, a snapshot generated by the thing under test, a
  constant asserted against itself). It passes by construction and can never disagree with
  the code. Expected values come from an independent source: a known-good literal, a worked
  example, the spec.
- **Untriggerable** — nothing the implementation could do would turn it red. Ask what
  single-byte change would break it; if there is none, delete it.

When a test needs heavy mocking to exist, the code is too coupled — the test is telling you
about the design, not about itself.

## Done

Every new behaviour has a test you watched fail for the right reason and then watched pass,
the relevant suite is green, and the output is clean — no stray warnings, no skipped test
you meant to come back to.
